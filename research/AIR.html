AIR Constraints

From execution trace to polynomial constraints — how AIR describes "correct computation" as an algebraic property, and why that's a different shape of constraint system than R1CS.

Srishti Rathi · Technical Notes · March 2026

Start with the trace

Run a program and record its state at every step — register values, memory, program counter, whatever the machine tracks — and you get a table. Each row is one step of execution; each column is one piece of state. This table is the execution trace, and it's the raw material every STARK-style proving system starts from.

step pc a b acc
00110
11121
22233
33356

On its own, this table proves nothing. Anyone can write down a table of numbers. What turns it into a proof of correct execution is a set of rules that say which tables are actually valid — and that's what an AIR is for.

What AIR actually says

AIR stands for Algebraic Intermediate Representation. It's a way of expressing "this trace is a valid execution" as a set of polynomial equations that must hold between rows.

Instead of writing "row 2 equals row 1 plus row 0" as ordinary code, an AIR states it as a constraint that must evaluate to zero at every row where it applies. For a Fibonacci-style accumulator, the transition constraint might read: the value in the accumulator column at the next step, minus the sum of the current two values, equals zero.

execution trace (table of values) → transition constraints (row → row) → boundary constraints (fixed rows) → one algebraic object

Two kinds of constraints usually show up together. Transition constraints govern the relationship between one row and the next — they encode the machine's step function. Boundary constraints pin down specific rows, such as requiring the first row to match a known public input, or the last row to equal a claimed output.

From table to polynomial

The reason this table can turn into a succinct proof is interpolation. Each column of the trace is treated as evaluations of some polynomial at a set of points — typically the powers of a root of unity, since that's what makes FFT-based interpolation fast. Once every column is a polynomial, "the constraint holds at every row" becomes "this constraint polynomial is zero on the entire evaluation domain," which is a statement a verifier can check probabilistically instead of row by row.

column of values → interpolate over a domain → trace polynomial → constraint polynomial → low-degree test (FRI)

A constraint polynomial that's supposed to vanish on the trace domain will be divisible by the vanishing polynomial of that domain. Dividing it out gives a quotient polynomial — and checking that quotient has the expected low degree is exactly the job FRI is built to do.

AIR versus R1CS

R1CS — Rank-1 Constraint System — is the other common way to express "this computation was done correctly," and it's worth contrasting the two directly, since it's easy to lump all constraint systems together.

Property AIR R1CS
Shape A table (trace) plus row-to-row rules A flat list of individual constraint equations
Repetition One rule applies uniformly across every row Each step of a loop is usually its own constraint
Natural fit Repeated, uniform computation — VM execution, hashing Arbitrary, one-off arithmetic circuits
Typical partner STARKs, via FRI and Merkle commitments SNARKs, via pairing-based or other polynomial commitments
Compiling a loop One transition constraint, many rows The loop is usually unrolled into repeated constraints
Neither shape is strictly more powerful than the other — they're different ways of expressing the same underlying idea, chosen because they pair naturally with different commitment schemes. AIR's row-uniformity is what makes it a good match for machines that execute the same step function over and over, like a zkVM.

Why the "algebraic" part matters

Calling it an algebraic intermediate representation is not decoration. The whole reason this is useful is that "every row satisfies this rule" can be restated as a single polynomial identity over an entire domain, and polynomial identities are exactly the kind of statement that commitments, random sampling, and low-degree testing know how to check efficiently — without the verifier ever touching the full trace.

Takeaway

An execution trace is just a table until an AIR gives it rules. Those rules — transition constraints between rows, boundary constraints on specific rows — turn "did this program run correctly" into a claim about polynomials.

That reframing is what lets a STARK prover commit to the trace, fold it down with FRI, and let a verifier check a handful of points instead of replaying the whole computation.
