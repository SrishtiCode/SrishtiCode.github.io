zkSync Airbender

A study of Airbender's prover architecture — how a production RISC-V zkVM turns the ideas I built from scratch (fields, AIR, FRI) into a system fast enough to prove real Ethereum blocks.

Srishti Rathi · Prover Architecture Study · June 2026

Why I studied it

After building a STARK prover and a KZG commitment scheme from scratch, the natural next question was: how do these same ideas hold up once proving speed, hardware, and real workloads enter the picture? Airbender is ZKsync's RISC-V proving system, and it was a useful case study because it is transparent, STARK-based, and open source — the same family of proof system I'd already implemented a small version of, just under very different performance constraints.

What Airbender proves

Airbender generates ZK proofs of RISC-V bytecode execution. Instead of hand-writing circuits for each program, any code compiled down to the RISC-V 32-bit integer instruction set — with multiplication extensions — can be run through the same proving pipeline. That includes EVM bytecode, WASM, or ordinary Rust, since it all eventually becomes RISC-V. In ZKsync's newer stack this is the basis for a "what you execute is what you prove" design: the same RISC-V trace that ran the program is the one that gets proven, rather than maintaining a second, separate circuit implementation of the VM.

program (EVM / WASM / Rust) → compiled to RISC-V → execution trace → AIR constraints → STARK/FRI proof

Reading the architecture

The pieces that stood out, mapped against the fundamentals I'd already built:

Field choice

My own prover used a field chosen mostly for clarity while learning. Airbender is built over the Mersenne31 prime field, chosen specifically because its arithmetic maps efficiently onto modern hardware — a reminder that field selection is itself a performance decision, not just a correctness one.

Execution model

The prover follows a fairly standard fetch–decode–execute loop over the RISC-V program, but processes it in large chunks — on the order of millions of cycles at a time — and stitches proofs of separate chunks back together using memory arguments. This is the same "trace → constraints" shape as the STARK I built, just decomposed to make long executions tractable instead of proving one flat trace end to end.

Machine variants

Rather than one fixed circuit, Airbender uses configurable "machine variants" that enable or disable feature sets depending on context — general-purpose execution versus specialized recursive proving, for instance. It's a modular take on constraint design: the AIR isn't one monolithic thing, it's assembled per use case.

CPU/GPU split

In GPU configurations, the CPU handles RISC-V simulation and trace generation while the GPU takes over witness generation and the heavier proving steps. Splitting the pipeline this way lets each processor do the part of the work it's actually suited for.

Where it lands, practically

Aspect My from-scratch STARK Airbender

Field Chosen for simplicity Mersenne31, chosen for arithmetic efficiency
Trace handling One flat execution trace Chunked traces stitched via memory arguments

Hardware target Single-threaded CPU CPU/GPU split, scales across GPUs
The interesting part wasn't that Airbender uses different concepts — it's almost entirely the same vocabulary I already had: traces, AIR, commitments, FRI. What's different is every decision has been pushed toward throughput, because the target is proving Ethereum blocks in the time it takes to read this sentence.

Takeaway

Building a STARK prover from scratch gave me the vocabulary. Reading Airbender showed me what that vocabulary looks like under real constraints — chunked traces instead of one flat pass, a field picked for hardware efficiency instead of convenience, and constraint systems that are assembled per use case instead of fixed in advance.

The gap between an educational prover and a production one isn't the theory. It's every decision made once speed, memory, and hardware stop being optional.
