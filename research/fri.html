FRI From Scratch

How low-degree testing works, why FRI repeatedly folds a polynomial, and how the commit–fold–query loop fits into a STARK proving pipeline.

Srishti Rathi · Technical Notes · 2026

The problem FRI solves

In a STARK, the prover commits to large vectors of field elements that are supposed to be evaluations of low-degree polynomials. The verifier cannot afford to download every value, interpolate the polynomial, and calculate its degree directly.

FRI — Fast Reed–Solomon Interactive Oracle Proof of Proximity — gives the verifier a cheaper way to test whether the committed evaluations are close to a polynomial below a required degree bound.

evaluations → commit → fold → commit again → repeat → query

Why low degree matters

A STARK turns execution correctness into polynomial identities. Trace columns become polynomials, AIR constraints become algebraic relations, and the resulting polynomial claims come with degree bounds. If a prover could replace those objects with arbitrary high-degree functions, the verifier's algebraic checks would no longer establish what they are supposed to establish.

FRI is not the part that proves the program's transition constraints. Its job is to test the low-degree property of the polynomial data produced by the earlier stages of the STARK.

Commit to the evaluation layer

Suppose f(X) has been evaluated over a multiplicative domain. The prover places those evaluations into a Merkle tree and sends only the root. This fixes the entire layer before the verifier's next random challenge is known.

f(x₀), f(x₁), …, f(xₙ₋₁) → Merkle tree → root

The folding idea

Write the polynomial by separating its even and odd powers:

f(X) = f_even(X²) + X · f_odd(X²)

The verifier samples a random field element β. The prover then defines the next polynomial by mixing the two halves:

g(Y) = f_even(Y) + β · f_odd(Y)

If f has degree roughly d, its even and odd parts have degree roughly d/2. The new polynomial therefore has a much smaller degree bound.

degree d → fold with β₀ → about d/2 → fold with β₁ → about d/4

Folding directly from evaluations

For opposite domain points x and -x, the even and odd pieces can be recovered directly from their evaluations:

even = (f(x) + f(-x)) / 2
odd = (f(x) - f(-x)) / (2x)

So the next-layer evaluation is:

g(x²) = (f(x)+f(-x))/2 + β · (f(x)-f(-x))/(2x)

This is useful in an implementation because the prover can fold evaluation vectors without interpolating a new polynomial at every FRI round.

Commit → challenge → fold

The order is essential. The prover first commits to the current layer. Only after the commitment is fixed is β sampled. In a non-interactive STARK, Fiat–Shamir derives that challenge from the transcript.

layer → Merkle root → transcript challenge β → fold → next layer

The process repeats, halving the layer in a binary FRI construction until the remaining polynomial is small enough to check directly.

1024 → 512 → 256 → 128 → … → final layer

Why queries are still needed

Merkle roots only show that the prover fixed each layer. They do not show that one layer was honestly obtained by folding the previous layer. After all commitments are fixed, the verifier chooses random query positions.

For a query, the prover opens the required values from one layer together with their Merkle authentication paths. The verifier checks those paths, recomputes the fold using the round challenge, and compares the result with the opened value in the next layer.

open pair → verify Merkle paths → recompute fold → compare with next layer

Why random queries give confidence

If the original data is far from every low-degree polynomial, the prover cannot generally make all of the committed layers behave like honest folds. Random query paths are used to expose inconsistencies. Repeating the test across multiple independently sampled queries reduces the chance that malformed data escapes detection.

FRI's formal soundness is a Reed–Solomon proximity-testing statement. Concrete security depends on parameters such as the code rate, domain size, folding strategy and number of queries; it is more subtle than simply saying that one random query detects every bad polynomial.

Why low-degree extension comes first

Before FRI, a STARK normally evaluates its polynomial over a domain larger than the original trace domain. This is the low-degree extension. The extra evaluations introduce redundancy: a genuinely low-degree polynomial cannot take arbitrary values over the enlarged domain.

trace → interpolate → evaluate on larger domain → commit → FRI

Where FRI fits in a STARK

By the time FRI runs, execution correctness has already been translated into algebraic constraints and polynomial claims. FRI provides the low-degree-testing layer that makes those claims efficiently checkable.

execution trace → AIR constraints → polynomial claims → LDE → FRI

Takeaway

FRI replaces the expensive instruction “reconstruct this huge polynomial and check its degree” with a sequence of smaller commitments and random consistency checks.

The prover repeatedly commits, receives a challenge, and folds. Once all layers are fixed, the verifier queries a few paths and checks that the folds were performed consistently.

The core mental model is: commit → challenge → fold → repeat → query. That is the heart of FRI and the low-degree-testing machinery behind a STARK.
